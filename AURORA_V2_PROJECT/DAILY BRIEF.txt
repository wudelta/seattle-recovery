DAILY BRIEF

every file created needs to have accompanying documentation. each file needs to have:

id: system generated id.
name: the actual file name.
date created: date created.
date modified: date last modified.
created by: wu, minion or process (this should never be me or any other user).
parent dependencies: meta field. all files or processes that depend on this file. this will make it easy to identify dead code. if nothing uses it, it isn't needed.
child dependencies: meta field. all files or processes that this requires to work. this make troubleshooting easy. if it doesn't work, run all the tests on child dependencies and figure out where it breaks. in fact, we can make it self-healing in the process.
constraints: the rules. tho shalt and tho shalt not stuff. this is for the minions. each time one is called, it reads it's own constraints and writes code that complies.
description: a human readable description of what it does.
description audiences: meta field. who can read this description. anyone, stakeholders and investors, developers, etc. the idea is to include it in documents prepared for a specific consumer.
locked: boolean. before a minion updates a file it must check to see if it's locked or not. this is a failsafe to keep minions and processes from destroying code. our current /destroy process could be invoked on working code an obliterate it. this is fine in the case of an under construction page. not so good for a critical component that users depend on.

where we are going, is to "take the monkey out of the mix". code should not be written or edited by humans. each time a file is created or modified, the corresponding tests and documentation are updated. trouble shooting, testing, fixing, documenting, will all be automated.
